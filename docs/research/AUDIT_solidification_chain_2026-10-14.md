# Solidification and precipitation chain: physical audit

Requested record date: 2026-10-14. Inspection completed across the local date boundary into 2026-10-15.
Baseline: `research/solidification-astra`, `835466fabca27d0209b29599fde7fa05a9b9ee75`.

Companion: [implementation specification](SPEC_solidification_2026-10-14.md).

## 1. Outcome and scope

The historical `multiElementScheil` defect is **already corrected at this baseline**. The current Python solver uses pycalphad equilibria of successive residual liquids, rather than the former temperature power law and independent constant-k composition curves. `isEmpirical: false` identifies that thermodynamic calculation; it is not evidence of accuracy or validation. Replacing this already-replaced implementation is not the next job.

The remaining chain cannot establish final LPBF microstructure or precipitation strength for the priority alloys. Its served problems include use of the wrong thermal observable for Ti64 transformations and loss of spatial support when thermal summaries are coupled to nonlinear models. Unsupported precipitation quantities reproduce at direct-function level, but have no served route today. There are also reproducible atom-inventory/status defects in Scheil termination. Existing honest unavailable states, P6 keyhole guards, and P7a spacing restrictions must be retained.

Three independently scoped sub-agents inspected (a) thermodynamics/database suitability, (b) segregation/CET/transformation/precipitation physics and (c) thermal coupling/UI/identity. The integration owner checked sources, merged the findings and reran their scripts. Source reads and `rg` were used directly; no graph-derived completeness assertion is made. `CLAUDE.md`, `RULES.md`, relevant `PROOF.md` records and the integration constraints were consulted. Historic PROOF entries are context, not fresh validation.

All seven requested Python modules and all four named UI components were covered, with necessary dependencies, legacy CFD producers, service transport and contracts. No experimental validation or blind test was performed. No measured melt-pool-depth dataset was opened, imported, fitted or compared. The explicitly prohibited PDFs, archives and spreadsheet were not opened. Paper text was extracted with `pdftotext -enc UTF-8` from explicit permitted filenames; no library-wide PDF extraction was used. No package was installed, commercial TDB downloaded, personal email sent, or external model used.

## 3. What is already appropriately contained

- Python CALPHAD no longer recovers from an unavailable database with empirical phase curves. `multiElementScheil` now comes from the stepwise kernel (`calphad_solver.py:1475-1633,2035-2120`). The browser model still has empirical `fs^0.7`, composition clamps and phase heuristics (`src/physics/calphadMultiComponentSolver.ts:312,370,532-538`), but the Python-off path is labelled empirical/client screening; the Scheil tab says “client model (not CALPHAD)”. It must remain an explicitly isolated demonstration or be retired, not be adopted as a second scientific authority.
- P6 withholds G/R/cooling for an unmatched keyhole depth leg. Do not replace that guard with depth-derived slopes. No chain result should become available because a keyhole depth scalar exists.
- P7a removed universal numerical PDAS and SDAS from the served Python path. The remaining PDAS alternatives are a dilute Ni-Nb model transferred to IN625/IN718 with validity limits. They are neither those full commercial alloys' measured spacing nor a statistical uncertainty band (S04).
- The DuPont literature card distinguishes a terminal gamma/Laves **microconstituent** from CALPHAD LAVES phase amounts. IN625 has a separate binary Nb model and explicitly unresolved terminal species. Constant partition coefficients are legitimate assumptions in these restricted analytical models; their existence alone does not make the model fraudulent. The old temperature interpolation label was the historical disagreement (S02-S03).
- Priority-alloy TTT/CCT curves and hardness are unavailable in the current steel-only Li model. AlSi10Mg, IN625 and 316L direct requests reject unsupported registry scope rather than using another alloy. This is a correct boundary; the generic LSW output is the remaining leak.

The segregation source header's assertion that neither IN625 source gives carbon constants is too broad: Cieslak Table VII gives a carbon partition coefficient. What remains missing is a complete source-bound carbon trajectory and the saturation-line/class-II parameters for that alloy, so this does **not** justify enabling the pseudo-ternary IN625 model.

The generic coarsening coefficients are an **unsourced inventory**, not proposed replacements: gamma=0.045 J/m², equilibrium mole fraction=0.02, molar volume=1.1e-5 m³/mol, D0=1.2e-4 m²/s, initial radius=1.5 nm, and the 280 MPa / 9 nm strengthening curve (`kinetics_ttt_cct_solver.py:567-620`). Per-alloy activation energies and Ti64 registry Ms/Mf values are likewise not a verified kinetic parameter set (`alloy_registry.py:302,343-379`). The current concentration conversion is dimensionally consistent; no lingering LSW unit error is alleged. The defects are source/species/state scope and inappropriate output availability. Requested aging time is echoed while the solver generates a fixed illustrative time curve; it is not a thermal-history solution.

## 7. Reproducibility and limits

Run with the installed Python 3.12, without installing anything. Scripts resolve the repository from their own path, so invocation can be from any working directory. These repository-root examples print JSON to stdout by default:

```powershell
py -3.12 -X utf8 docs/research/scripts/check_solidification_thermodynamics.py
py -3.12 -X utf8 docs/research/scripts/check_solidification_kinetics.py
py -3.12 -X utf8 docs/research/scripts/check_solidification_coupling.py
git diff --check
```

Append `--output docs/research/scripts/check_solidification_<name>.json` only when explicitly regenerating a committed receipt; ordinary reruns do not rewrite tracked JSON. Each script captures source hashes and reproduces synthetic/algebraic defects. AST-extracted pure functions are used to avoid importing dataset loaders or running the thermal solve.
